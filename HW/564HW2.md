# Code Smell: Data Class

## A. ความหมายของ Code Smell

**Data Class Smell** คือ Data Class ที่เก็บแค่ Field อย่างเดียว มีแค่การเอาเข้าผ่าน Getter/Setter แต่ไม่เก็บพฤติกรรมเอาไว้ในคลาสเลย ทำให้จากหลักการ OOP แล้ว ข้อมูลและพฤติกรรมควรอยู่ด้วยกัน ถ้าคลาสมีแต่ข้อมูลจะทำให้:

* ข้อมูลถูกเปิดเผยให้คลาสอื่นดึงไปใช้ (ผิดหลัก Encapsulation)
* โค้ดที่ควรจะเป็นการทำงานของคลาสนั้นดันไปกระจายอยู่ในคลาสอื่นๆ
* ถ้ามีการเปลี่ยนโครงสร้างข้อมูลจะต้องตามไปแก้ Logic ในไฟล์อื่นๆ ที่มีการเรียกใช้ข้อมูลจากคลาสนี้

## B. ตัวอย่างโค้ดที่เกิด Code Smell

สมมติว่ามีระบบร้านค้าออนไลน์ เรามีคลาส `Order` ที่เป็น Data Class และมีคลาส `OrderService` ที่ดึงข้อมูลไปคำนวณ

```java
// --- Code Smell: Data Class ---

// 1. คลาสนี้ทำหน้าที่เก็บข้อมูลอย่างเดียว (Passive)
public class Order {
    private List<Item> items;
    private double taxRate;

    public List<Item> getItems() { return items; }
    public void setItems(List<Item> items) { this.items = items; }
    public double getTaxRate() { return taxRate; }
    public void setTaxRate(double taxRate) { this.taxRate = taxRate; }
}

public class Item {
    private String name;
    private double price;
    
    public double getPrice() { return price; }
    // ... getters and setters
}

// 2. Logic การคำนวณไปกองอยู่ที่ Service (Feature Envy)
public class OrderService {
    public double calculateTotal(Order order) {
        double subTotal = 0;
        // ต้อง "ดึง" ข้อมูลออกมาจัดการข้างนอก
        for (Item item : order.getItems()) {
            subTotal += item.getPrice();
        }
        // คำนวณภาษีข้างนอก
        return subTotal + (subTotal * order.getTaxRate());
    }
}
```

ปัญหาในโค้ดนี้: OrderService รู้เรื่องภายในของ Order มากเกินไป (รู้ว่ามี Items, รู้ว่าต้องวนลูป, รู้สูตรภาษี) ถ้าเกิดใน Order เปลี่ยนวิธีเก็บภาษี ต้องมาแก้ที่ OrderService

## C. ตัวอย่างโค้ดที่ Refactoring แล้ว
ใช้เทคนิค Move Method ย้าย Logic การคำนวณกลับเข้าไปในที่ที่ข้อมูลอยู่ (คือคลาส Order)

```java
// --- Refactored: Rich Domain Model ---

public class Order {
    private List<Item> items;
    private double taxRate;

    public Order(List<Item> items, double taxRate) {
        this.items = items;
        this.taxRate = taxRate;
    }

    // Logic ย้ายเข้ามาอยู่ในคลาส (Encapsulation)
    public double calculateTotal() {
        double subTotal = 0;
        for (Item item : items) {
            subTotal += item.getPrice();
        }
        return subTotal + (subTotal * taxRate);
    }
}

// การใช้งานสะอาดขึ้น (Tell, Don't Ask)
public class OrderService {
    public void processOrder(Order order) {
        // เราแค่ "บอก" ให้ Order คำนวณยอด
        double total = order.calculateTotal();
        System.out.println("Total price: " + total);
    }
}
```

ผลลัพธ์: คลาส Order มีความฉลาดขึ้น (Smart Object) คลาสอื่นไม่ต้องรู้ว่าข้างในทำงานยังไง แค่เรียกใช้ Method ก็พอ

## D. กรณีที่ Code Smell นี้ไม่ได้บ่งบอกถึงปัญหา (ไม่ต้อง Refactor)
ในบางสถาปัตยกรรม Data Class เป็นสิ่งที่จำเป็น:

- DTO (Data Transfer Object):
  - เมื่อต้องการส่งข้อมูลระหว่าง Layer (เช่น ส่งจาก Database ไปยัง Frontend หรือรับ JSON จาก API) เราต้องการ Object ที่ทำหน้าที่แค่ห่อข้อมูลเพื่อส่งผ่านระบบ ไม่ควรมี Logic ซับซ้อน
- Functional Programming Style:
  - ถ้าเขียนโค้ดในสไตล์ Functional หรือใช้ภาษาที่แยก Data กับ Behavior ออกจากกันอย่างชัดเจน (เช่น การใช้ Struct ใน Go หรือ C) การมี Data Class เป็นเรื่องปกติ
- ORM Entity (บางกรณี):
  - Framework บางตัวต้องการ POJO (Plain Old Java Object) เพื่อ Map ข้อมูลลง Database การใส่ Logic มากเกินไปใน Entity อาจทำให้เกิดปัญหากับ Framework ได้
- Immutable Value Objects:
  - คลาสเล็กๆ ที่ใช้แทนค่าบางอย่าง เช่น Color(r, g, b) หรือ Coordinate(x, y) อาจจะมีแค่ Getter ก็พอแล้ว เพราะหน้าที่มันคือการเป็นตัวแทนของค่านั้นๆ
